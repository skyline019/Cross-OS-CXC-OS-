# 无 KV、无 CDC 的 xv6 原生 PMEM 文件系统设计

> **状态：本文是目标文件系统设计，不是已完成的 VFS 实现。** 现已另行实现[独立单文件发布实验核心](THESIS-DIRECTCORE-EXPERIMENT.md)，只覆盖最多 512 B、双根与有界分配/恢复；它不支持本文的目录、递归树、脏窗口和 VFS。此方案不使用 KV API、KV run、CDC、内容寻址、去重或 FCS 存储引擎；inode 表及目录加速只是文件系统内部结构。它与现有 v3 格式不兼容，讨论此方案不意味着删除仓库中已有 KV/CDC 代码。附带的[有界模型](../tools/check_directfs_design.py)仅检验抽象提交场景，不执行内核。关于 QEMU NVDIMM、NVMe 原生对照、窗口/链群/动态规划取舍，见[新架构](THESIS-QEMU-NVDIMM-NVME-ARCHITECTURE.md)。

## 1. 题面与设计取舍

题目要求：在 xv6 中设计原生 PMEM 文件系统，映射 QEMU 模拟的 NVDIMM，利用字节寻址绕过传统块设备栈，用缓存行刷写与正确的持久顺序保证所声明故障模型下的崩溃一致性，并与 xv6 原生 FS 比较延迟和实际吞吐。

本方案只保留四个必需机制：

1. **直接映射**独立 PMEM 地址，数据读写不走 `bio/log/virtio`。
2. **64 B 固定单元 + 八叉直接索引**，按文件偏移定位数据，不建立 KV、CDC 或追加日志。
3. **不可变 COW 对象 + 两个原子根指针**，所有需要同步的变更通过一次根指针发布。
4. **DRAM 引用计数和空闲位图**，保护两个根，回收不再可达的单元；不为回收而搬迁活数据。

这里的 64 B 是本仓 QEMU/Zicbom 实验的初始格式参数，不是所有硬件的事实。普通读写使用 PMEM 字节地址，但提交时以缓存行大小的 COW 单元写入；因此这不是 4 KiB 块设备，也不意味着 1 B 写只产生 1 B 持久写入。

```text
用户 read/write/fsync/rename
             ↓
        xv6 VFS / 打开文件
             ↓
  inode → 文件偏移直接索引 → PMEM 数据行
             ↓                  ↑
     COW 候选对象          DRAM 脏页/可选索引缓存
             ↓
  持久化候选 checkpoint → 原子替换非活动根指针
             ↓
   双根引用计数 / 空闲位图 / 延迟回收
```

为保持简单，首版没有持久 B 树、分形树、红黑树、LSM、倒排、并查集、ANN、段 manifest、后台压缩或自动去重。它们只能在发现具体瓶颈后，作为单变量可关闭优化引入。**“最优”是要通过给定负载证明的目标，不是对所有文件大小、线程数和硬件的预设保证。**

## 2. 设备、格式和地址

- 复用仓库的设备发现路线：本仓 QEMU 9.2 RISC-V `virt` 补丁提供独立 NVDIMM 和私有 FDT 节点；内核在 `kalloc` 前验证、映射设备，禁止普通物理页分配器占用该范围。未发现预期设备时失败关闭，不回退成伪 NVDIMM。
- 地址以 `PMEM_BASE + 64 × line_id` 计算，使用 64 位算术并检查溢出、对齐和设备范围。**持久对象只保存 32 位相对 line ID，不保存内核虚拟指针**；ID 0 为 NULL，保留区不能分配。
- 实验配置为独立 32 MiB 设备，即 `524288` 个 64 B 单元。32 位 ID 的格式上限和几何信息必须在挂载时验证；首版最大文件逻辑大小限定为设备大小，稀疏洞读零。实际可用数据容量还要扣除索引、双根保护与预留。
- 前两个不同缓存行分别放一个对齐的 **8 B 根指针词**，其余空间是可重用的 64 B 对象池。两个词不能处在同一实际刷写/故障单元中。只有确认平台实际缓存块为 64 B 的配置才使用本格式；否则拒绝按此格式作持久保证，或另行定义并验证格式。
- 使用新 magic/格式版本和独立镜像；v3 与本方案互不自动识别为同一格式。格式化是显式破坏操作，不自动格式化空白、旧版或损坏介质。现有仓库默认后端保持不变；未来通过单独构建配置选择该实现。

### 2.1 持久对象

所有字段使用固定小端编码和显式边界检查，不依赖 C 结构体填充或未对齐访问。

| 对象 | 大小 | 内容和作用 |
|---|---:|---|
| 根指针词 | 8 B | 低 32 位 checkpoint line ID，高 32 位指针校验；一次对齐原子存储。两个词位于不同缓存行 |
| checkpoint 记录 | 64 B | magic、格式、特性、64 位 epoch、inode 表根和高度、根校验、设备几何、记录 CRC |
| 八叉索引节点 | 64 B | `line_id[8]` 与 `expected_crc[8]`，每项各 32 位；节点本身的 CRC 由父节点或 inode/checkpoint 保存 |
| inode | 64 B | inode ID/代数、类型、大小、链接数、数据根 line ID/高度/根校验、目录父 inode、标志等 |
| 普通文件数据 | 64 B | 文件一个逻辑缓存行的实际字节，不带 KV key 或 chunk 指纹 |
| 目录项 | 64 B | inode ID/代数、类型、名字长度、名字和保留字节；当前 VFS ABI 对外最多 27 B 名字 |

可供实现核对的 checkpoint 布局：`0..3 magic`、`4..5 版本`、`6..7 特性`、`8..15 epoch`、`16..19 inode 表根 ID`、`20..23 根 CRC`、`24 高度`、`25..27 保留`、`28..31 设备单元数`、`32..59 卷标识/保留`、`60..63 CRC`。CRC 计算时将记录自身 CRC 字段视为 0。根指针词的高 32 位校验其 line ID 与固定格式盐；指向的 checkpoint 自己再校验内容。CRC 并非密码学认证，碰撞不属于理想协议模型。

inode 也可固定编码为 64 B：`ino:u32`、`tree_root:u32`、`generation:u64`、`size:u64`、`nlink:u32`、`type:u8`、`height:u8`、`flags:u16`、`tree_root_crc:u32`、`parent_ino:u32`、`parent_generation:u64`、`mtime_ticks:u64`、`reserved:u64`。`mtime_ticks` 是可选逻辑时间，不假装是 xv6 没有提供的真实墙钟时间。目录项名字的当前上限取自 `VFS_NAME_MAX=27`；扩展该上限必须同时修改用户 ABI，不能只改磁盘格式。

八叉节点没有 KV 语义。非空子指针记录该子对象的 CRC；顶层根 CRC 存在 checkpoint 或 inode 中。文件数据 CRC 是**格式化时固定的特性**：建议以关闭的配置作为性能基线，此时仅校验元数据，不能声称检测静默数据损坏；开启时叶指针保存数据行 CRC，读取时校验并报告代价。不能直接翻转已有卷的特性位而不重建所有受影响校验；消融使用分别格式化、内容相同的卷。目录项始终作为元数据校验。无论是否开启数据 CRC，故障测试都必须由外部内容 oracle 检查完整文件。

### 2.2 文件直接索引

每个 inode 的数据根指向稀疏八叉树；高度 0 表示根直接指向逻辑第 0 个数据行。高度为 `h > 0` 时，每层根据逻辑行号的 3 个位选择一个子指针；空指针代表全零洞。根不够覆盖新偏移时，以旧根作为新根的第 0 个子树向上扩展。目录使用同一机制，每个 64 B 数据行对应一个目录项位置。

- 文件大小 1 MiB 有 `16384` 个逻辑数据行，需高度 5；32 MiB 逻辑上限需至多高度 7。
- inode 表同样是直接索引；从至少 1 层开始动态增长，上限 4 层，最多覆盖 4096 个编号（0 保留）。这不等于能同时打开 4096 个文件：xv6 当前 `NFILE=100` 等运行时上限仍须单独处理。
- 单次事务对多个数据行修改时，同一路径上每个索引节点**只复制一次**。顺序写尽量批量预留相邻物理行，预留失败后允许非连续行；正确性不依赖连续性。
- 索引读取必须核验非空指针的范围、上下文类型和元数据 CRC；不能把目录记录当索引或越界地址。对同一物理行出现矛盾的预期类型/校验，失败关闭。

这是固定粒度文件映射，不是用户可访问的 KV 索引。可选 DRAM 缓存保存已验证的 `(inode 代数、数据根版本、逻辑行 → 物理行)`，缓存缺失时走持久树，容量不足不能改变结果。提交、删除和 inode 复用时在锁内更新或失效缓存；缓存不参与恢复判定。

## 3. 读写与 VFS 语义

### 3.1 工作状态

- 每个打开的 inode 有共享的 DRAM 工作状态，多个独立 `open` 看到相同已写内容，但各自文件偏移独立；`dup/fork` 按 xv6 的共享打开对象规则处理偏移。硬链接共享 inode，不复制数据。
- 可用普通 4 KiB **DRAM** 脏页作为缓冲，每页有 64 位有效/脏掩码，标记其中的 64 B 行；这不是 4 KiB 持久写。部分覆盖只读取所需旧数据行，完整覆盖不必读旧数据；`read` 先看脏行，再直接从 PMEM 读取其余部分。
- 建议首版每 inode 最多 64 KiB 已分配的脏页数据缓冲（16 个 4 KiB 页）、全系统最多 1 MiB，另将掩码/页描述符计入内存预算；限制的是**驻留页容量而非已修改字节数**。稀疏写可能只修改少量字节就占满配额。超过上限可以提前提交部分写、背压或返回短写；提前提交意味着未 `fsync` 的部分写**也可能**在崩溃后保留。容量和故障要计入测试。
- `write` 成功只保证数据进入共享工作状态，不承诺已持久化；`fsync` 成功保证调用前已完成的该文件写入包含在持久根内。内存压力触发的额外提前提交不改变这一承诺。每次事务最多处理预定义的脏数据上限；较大 `write` 可返回短写，调用方循环，不承诺任意大单次写跨多次提交后整体原子。
- `fsync` 失败且最终根词尚未写入时，保留所有 dirty 数据以便重试；不能悄悄清除。最后一次 `close` 可尝试同步并报告错误，失败后的 dirty inode 不得因关闭描述符直接丢掉。进程退出无法报告关闭错误，故应用需要显式 `fsync`。

### 3.2 命名空间

`create/mkdir/link/unlink/rename` 将涉及的目录项、目录 inode、目标 inode/link count 及 inode 表路径作为**一个**候选根发布；不能先发布半个 rename。目录项保存 `(inode ID, generation, name)`，inode ID 可复用，但 generation 必须匹配，序号耗尽时失败关闭。目录 `.` 和 `..` 可由 inode/父信息合成；目录硬链接、跨后端 rename、权限和符号链接等未实现能力必须明确拒绝或单独实现，不能宣称完整 POSIX。

目标版本可支持最后链接的 unlink-open：删除目录项并将 `nlink` 置 0，但只要打开对象仍存在就继续保留 inode；最后关闭后再从 inode 表移除。崩溃后打开引用不复存在，恢复时扫描 `nlink=0` inode 并安全清理。目录删除、替换、非空目录、跨目录移动及目录环须有明确检查。命名空间操作不得把另一个脏文件的未同步 size/data 意外发布：更新链接数时以最新**已提交** inode 为基础，工作数据仍由其自己的 `fsync` 发布。

截断必须处理尾部和洞：缩短时 COW 清零新 EOF 所在行的尾部并剪除之后的指针；之后再扩展时未写部分读零，不得暴露旧字节。写入从用户内存分段复制，失败时返回已成功接受的字节数或错误，并正确维护共享偏移。

## 4. 一次根指针发布：提交和失败边界

根指针词指向一个**不可变 checkpoint 记录**。格式化后两个槽可指向同一初始记录；不同 checkpoint 使用严格递增的 64 位 epoch。相同 epoch 只允许两个槽指向**同一条**记录，否则失败关闭。

一次文件 `fsync` 的建议协议：

1. 固定待提交的脏行和对应 inode 状态；根据两个有效根和所有在途预留计算**实际需要的**新数据、索引节点、inode、inode 表路径和 checkpoint 单元，连同必要应急预留预检。保留的所有单元互不重叠，也不覆盖任一有效根可达对象。
2. 构造并写入新数据行、COW 数据路径、inode、COW inode 表路径和新 checkpoint 记录。合并相同路径的复制；无关文件、目录和索引子树继续引用旧对象。
3. 对全部新对象发出缓存行 clean/flush，再执行一次持久排序/完成屏障。checkpoint 记录也在这一批中；在此之前提前写回的新行对旧根不可见。
4. 对非活动槽执行**一次对齐 8 B 原子存储**，将其指向新 checkpoint；刷写该槽所在行并执行第二次持久屏障。只有第二次屏障完成后，`fsync` 才能报告成功。
5. 在锁内切换活动根、安装/失效 DRAM 缓存，并按两个新根更新引用计数。只有根词已持久后才退役原槽的旧引用；dirty 位只清除本次成功发布的内容。

此方案不在槽内原位改写 checkpoint 头，也不需要先使旧槽失效：槽的原子词只能是旧指针或新指针，而新指向的不可变 checkpoint 和对象已在步骤 3 持久化。它比在槽内分三阶段覆盖头更短，但依赖明确的 **8 B 故障原子存储**和刷写/屏障持久域假设。两个根槽、checkpoint 记录和所有新对象的写流都必须进入故障轨迹。这里是两次**协议级 drain**；现有 `pmem_flush()` 自身含同步指令、`pmem_persist()` 每次还执行 fence，实际实现需提供正确的批量 flush 接口并记录真实执行的全部屏障，不能仅修改计数器以制造“两次”。

- 在根词**写入之前**失败，可放弃私有预留、保留 dirty 缓冲；两个旧根仍可恢复。
- 根词已经写入后，即使最后 flush 尚未完成，也可能提前写回。此时出错不能断言回滚：应完成已知可行的持久化，或停止写入并在重挂载后判定；不得释放可能已发布的对象。
- 单个已 `fsync` 文件在协议假设内恢复到完整旧版或完整新版；成功返回后应为新版。跨文件 `write/fsync` 不默认形成联合事务；命名空间复合操作则由一个根覆盖。

## 5. 空间回收：不需要搬迁式 GC

64 B 单元由可重建的 DRAM 空闲位图分配，循环游标优先寻找相邻空间，但离散空间也可用。对象只要被**任一有效根**、在途事务或受保护读者引用，就不能分配为新对象。文件数据与元数据都是不可变 COW；旧版本在两个根都不再引用后直接变成空闲单元。

为避免每个小写都扫描整棵文件系统，可在 DRAM 维护每个对象的**实际入边引用数**：两个根槽各贡献一条根边，每个仍可达的父对象的每条物理子边只计一次。物理所有权图是 `checkpoint → inode 表 → inode → 文件树 → 数据`；目录项中的 inode ID 是名字语义，不是额外的物理所有权边，因而硬链接或目录父关系不会形成引用计数环。发布成功后先加入候选根中实际可达的新对象/新根边，再删除被替换槽的旧根边；计数降为 0 的对象排入延迟释放队列，处理时才递减其子边。**同一父对象被两个根共享时，不能把该父对象的子边计算两次。** 队列和计数仅是优化，崩溃后不信任它们。

如果旧槽阻止回收，可以把它的原子词刷新为当前槽指向的**同一个 checkpoint**，刷写并完成屏障，再退役旧槽引用。此操作不分配新 checkpoint，也不增加 epoch；崩溃时该槽仍只能是旧指针或当前指针。它可能增加前台延迟，因此基准必须计入刷新、队列处理和后台工作，而不是只计一次普通 `fsync`。

- 延迟队列可每次处理有界数量，避免删除大文件时长时间持锁；低空间时需继续处理或安全背压，不能把尚未处理的单元当空闲。
- 普通增长操作预留一小块经过计算的元数据应急空间，供删除/截断等不扩大活数据的操作完成 COW；必须按最大树高和多目录操作的**实际最坏对象数**预检。可以先刷新旧槽并处理队列，再重新评估；若仍不足，则返回 ENOSPC，不破坏旧根。不能保证物理满盘时任意覆写仍能成功。
- 首版无需整理碎片才能获得容量：固定大小单元可分散分配。连续分配只是优化；若实测顺序读碎片成为瓶颈，再评估可关闭的整理，而不是把整段搬迁和 manifest 作为必需机制。
- 轮转游标只分散软件分配位置，不等于硬件磨损均衡。QEMU 不模拟 NVDIMM 磨损，软件 store 字节也不是器件物理写入量。

32 MiB 设备共有 524288 个单元：一份位图约 **64 KiB**，32 位引用计数数组约 **2 MiB**，再加类型/遍历状态、预留位图和队列。xv6 需分配分页的元数据数组而非假设连续大块内核内存；引用计数溢出、类型冲突或资源不足时必须停止回收/失败关闭。

## 6. 恢复与故障模型

启动时读取两个原子根词，验证指针词、checkpoint 范围/格式/CRC 和 epoch，选择最新记录；两个相同指针的等 epoch 是合法根刷新。沿**两个**有效根遍历 inode 表和文件树，检查边界、树高度、类型、元数据校验及结构，重建入边数、空闲位图、inode ID 可用状态和目录缓存。共享对象只遍历一次，但各根边都要计数。数据 CRC 可按读取时检查或显式 scrub；关闭数据 CRC 时不能宣称能检测数据静默损坏。

正常完成格式化的卷应有两个合法槽；槽词校验无效、或根词看似合法但所指对象图损坏时，默认拒绝挂载或只读/人工恢复，不能悄悄回退并声称已确认的 `fsync` 一定还在。格式化被中断而只初始化一个槽也不当成正常卷；需显式处理。若旧根损坏，不能仅忽略它再回收其可能引用的区域。损坏恢复、校验碰撞和真实器件故障是单独问题；正常崩溃协议假设受保护旧数据不发生无关的介质损坏。

持久性假设必须单列：缓存块大小与地址有效，根词故障原子，clean/flush 与 fence 能按约定到达持久域，未 flush 的数据可以提前回写或部分持久。仓库默认 `pmem_flush` 是 touch+fence；可选 `CBO.CLEAN` 在 QEMU TCG 只验证指令执行路径，不模拟真实缓存持久化。普通宿主文件后端和杀 QEMU 进程不等于真实掉电。真实硬件必须另行确认缓存能力、块大小、持久域及原子性。

## 7. 性能成本：先算账，再测量

以下都是**编码层静态估算，不是内核实现、物理写放大或实际性能数据**。假设缓存行 64 B，数据 CRC 关闭，无额外根刷新、空间预留/回收写入；节点和 checkpoint 都整行写，根槽只写 8 B。实际性能还包含旧节点读取、CRC、锁、cache miss、分配和后台工作。

| 同步工作量 | 条件 | 新对象 store + 根词 | 软件请求比 |
|---|---|---:|---:|
| 64 B 对齐覆写 | 1 MiB 文件、文件树 5 层、inode 表 3 层 | `(1 数据 + 5 节点 + 1 inode + 3 表节点 + 1 checkpoint) × 64 + 8 = 712 B` | `11.125×` |
| 4 KiB 对齐覆写 | 文件 4 KiB、文件树 2 层、inode 表 3 层；64 个数据行共享 9 个新数据树节点 | `(64 + 9 + 1 + 3 + 1) × 64 + 8 = 5000 B` | 约 `1.22×` |

第一个示例请求刷写 11 个新对象行和 1 个槽行，使用两次协议级持久屏障；这里的字节数统计 **store**，不能把 12 条 flush 请求直接当成物理写入。1 B 写仍需至少一个 64 B 数据行；跨行写会增加数据与路径。顺序数据的完整八叉树约有 `N/7` 个节点，即数据单元数量约 14.3% 的额外节点；稀疏文件、两代根和预留可能更高。

已有 v3 的历史 64 B 覆写记录是约 8320 B 软件请求，但它来自另一套实现及工作负载。712 B 不能与之直接当作实测倍率；需要在同设备、同 API、同数据、同持久模型下运行实现并统计前台与回收总成本。

### 简洁与高性能的边界

- 热读可使用受版本保护的 DRAM 行映射；顺序读把相邻物理行合并复制。冷读仍要 traversing 索引并验证元数据，索引缓存占内存，不能只报缓存命中场景。
- 初版用全局睡眠锁串行提交和回收、读时保护可达对象，最容易证明正确，但多写者会受全局锁限制，**不是可扩展性最优**。实测锁争用后，可演进到每 inode 锁并行准备、短暂全局根提交锁和读者保护：提交前重新解析最新 inode 表，确认 inode 代数与数据根未变化、合并最新链接数后重建 inode 表路径；所有在途预留需同时受保护。条件不满足则重试，不能覆盖别的文件更新。
- 数据 CRC、目录 DRAM 哈希和更大的脏缓冲都是独立消融项；任何哈希命中都必须比较完整名字。批量 `fsync` 可节省 checkpoint，但引入等待和跨事务顺序问题，首版不假定收益。

## 8. 可实现路径与验收

1. **原型**：单独构建配置复用 `pmem.c` 设备发现及 flush 接口；新增直接索引/分配器与文件/VFS 适配，不在运行路径上调用 `pm_put/pm_get/pmcdc/pmstream`。先在 `/pm` 挂载保留 xv6 原根，若题目要求完全替换根文件系统须另做启动和验收。
2. **功能**：至少验证 1 MiB 文件、128 个持久文件、64 B/4 KiB 随机覆盖和追加、稀疏洞、截断、rename、硬链接、unlink-open 和重启；确认 27 B 名称、128 B 路径及打开文件等现有 ABI 限制。目标不是当前已实现功能。
3. **崩溃**：对实际内核记录的 data/node/inode/checkpoint store、flush、drain 和槽词原子 store，在每个边界做提前回写模型及 NVDIMM 进程重启；检查旧/新完整内容、其他文件不丢、两个根保护。故意漏刷数据/记录/根词、提前发布、提前回收及错误引用计数必须被 oracle 检出。
4. **空间**：连续覆写、全新写入、删除大文件、两槽相同根刷新、接近满盘与 ENOSPC 重启；统计活数据、旧根 pin、预留、待回收单元及尾延迟。
5. **对照**：在补丁 QEMU 独立 NVDIMM 下验证 QMP/FDT，然后以相同内容、offset、文件大小、调用和成功次数比较 `write+fsync+readback`。原生 xv6 路径的 `fsync` 当前是全局日志同步，virtio 不协商设备 flush；先如实报告契约差异。若实现 native flush 对照，须验证日志次序及失败处理，而不是仅开启 feature 位。
6. **统计**：区分易失 EMUL、实验 NVDIMM、NVDIMM+Zicbom；至少 10 次独立测量启动、固定种子、预热和完整 raw 数据，报告 p50/p95、实际计时吞吐、失败数、软件 store/flush/读取字节、锁等待及回收成本。共享原生对照文件尺寸不超过其上限，1 MiB 作为 PMFS 扩展实验另列。数据 CRC、映射缓存和并发分别做消融，保留负结果。

## 9. 已执行的设计模型与边界

运行 `python3 tools/check_directfs_design.py`。该独立 Python 模型针对**一个** COW 文件更新，将数据、inode 和不可变 checkpoint 各抽象为两条持久行，枚举操作边界上所有脏行的提前回写子集；另检查一次根槽刷新，并比较一个共享 DAG 的增量引用计数与重建结果。它包含旧根覆盖、槽刷新持久化前复用、暂存重叠、漏刷数据/记录/槽、提前发布、提前丢 dirty 以及误减共享子边等负控。

模型假设根词原子、元数据校验无碰撞及 flush/fence 语义正确；数据完整性由外部 oracle 检查。它**没有**运行内核 C、完整八叉树、并发、真实设备或全部工作负载。模型通过只能说明该有限抽象没有发现反例，不能当成文件系统实现、物理掉电证明或性能成绩。
