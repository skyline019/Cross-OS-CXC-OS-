# 对照原题的收敛设计：KV/CDC 与字节寻址 PMFS

> **性质：设计提案，不是已实现的内核或新的 QEMU 性能结果。** 代码现状以 `024b115` 的 v3 原型、[语义](SEMANTICS.md)和[维护说明](MAINTENANCE.md)为准。本轮另外提供一个独立、有界的[单次提交设计模型](../tools/check_txn_design.py)；它不是内核测试，更不证明物理掉电安全。

## 1. 重新对齐题面

目标是在 xv6 内核中实现原生持久内存文件系统：发现并映射 QEMU 模拟的 **NVDIMM**，利用字节寻址组织数据和元数据，绕开传统块设备栈，以缓存行刷写和正确顺序保证所声明故障模型下的崩溃一致性；最后与 xv6 原生 FS 比较延迟和实际吞吐，并交付可复现原型、测试和论文。

因此设计主线应是 **字节寻址数据路径 + 一个清晰的提交点 + 可恢复的空间回收**，而不是先叠加更多索引名称。已有公开 KV、CDC/stream 和 VFS 是要保留的能力，而不是另起一个没有它们的文件系统。

| 题面要点 | 现状 | 需要补齐或验证 |
|---|---|---|
| NVDIMM | 本仓补丁的 QEMU 9.2 RISC-V `virt` 可冷插拔独立 NVDIMM，经私有 FDT 发现 | 使用该后端做正式工作负载；这不是上游通用 `virt`、ACPI/NFIT 或真实器件 |
| 字节寻址、绕开块栈 | PMFS 不走 xv6 的 `bio/log/virtio`，但 `pmdev` 文件数据和快照仍以 4096 B 页复制/写入 | 对持久化记录按实际范围寻址和刷写，计入校验、对齐和元数据成本 |
| 文件与接口 | 普通文件经 CDC/固定分块、KV run、inode extent；40 inode、4 extent、每文件最多 1024 B | 保留 KV/CDC/VFS，扩展文件大小和目录规模；当前不是完整 POSIX |
| 持久提交 | 普通文件数据同步通常先 seal run 并发布根，再写 inode 快照并再发布根 | 在兼容性验证通过的前提下，先将同一文件事务收敛为一次根发布 |
| 回收 | 两个有效根保护页，支持显式全链 COW 压缩及页复用 | 近满盘预留、有限工作量的安全回收和长期写入；当前无自动增量 GC |
| 证据 | 有 QEMU 进程重启、有限范围事件重放与同 API 短批实验 | 正式 NVDIMM 负载、同契约消融、不同故障模型和论文定稿更新；历史 EMUL 与原生 xv6 的持久契约不等价 |

默认 `pmem_flush` 是 touch+fence，并非硬件缓存写回；可选 Zicbom 指令路径也不意味着 QEMU TCG 模拟了真实缓存或持久域。后端应明确区分易失仿真、软件持久模型和经平台验证的持久域；未来真实持久模式若无法确认刷写指令、块大小及持久域，应拒绝作物理持久承诺，而不是静默降级。真实硬件结论必须另行验证。

## 2. 选定的最小架构

```text
普通文件 / 目录 VFS                 公开 KV / CDC / stream
             \                         /
              \   一个事务与可恢复记录层  /
               → 追加不可变记录 + 逻辑 extent → DRAM 精确索引
               → 候选对象/manifest 持久化 → 双槽 checkpoint
               → PMEM 字节范围 store / flush / fence
```

同一套持久记录承载文件数据、inode/dentry 更新及公开 KV；CDC 负责选取文件分块，文件 extent 引用稳定的内部 chunk ID，KV 保留原 API 和保留键空间。DRAM 索引可重建，不是持久事实的唯一来源。初版保留现有全局锁，先做对再用实验决定是否拆锁。

实现分两步：**先以现有 v3 格式改进一次提交，保持行为兼容；再在独立 v4 格式上做真正的变长记录和更大文件。** v4 是达到题面字节粒度及规模目标的建议，不应误称现有功能。两种格式各自明确识别，v3 卷继续按 v3 处理；v4 只在显式格式化新卷时创建。未经完成并验证的迁移工具，不原位升级、不自动格式化旧卷，也不声称支持完整迁移。

### 2.1 数据与命名空间

- 建议 v4 采用固定大小的段，例如 **64 KiB 作为初始可调实验参数**；段内为追加记录，不允许单条记录跨段。记录包含类型、编码长度、逻辑 ID、事务版本、校验和及负载，按当前平台确认的缓存行边界对齐。文件 chunk、KV、inode 更新和 `(parent inode, name)` 目录项共享这一机制。
- extent 至少包含 `(file offset, length, chunk ID, chunk 内偏移)`。文件局部覆写只产生被修改的 chunk/范围及必要元数据；未改变的部分继续引用旧 chunk。涉及变长分块时，需要检查所有边界并保留左右未改范围，不能只比较哈希。
- CDC 与固定分块均保留并消融。初版不承诺去重；若加入跨文件复用，必须比较实际长度和字节，并在回收中保留所有引用。64 位指纹不能单独证明内容相等。
- 根据工作负载先选择简单有序表或哈希表做 DRAM 精确索引；索引不足时必须有**完整且正确**的回退扫描，或明确拒绝，而不是返回不完整结果。当前 `0xC0` 内部 chunk 键共享粗桶，应针对偏斜测试。持久红黑树、Bε/分形树、倒排索引、ANN 和并查集都不是首版必需品。
- 逻辑 chunk ID 而非裸物理地址是文件 extent 的持久身份。段搬迁后重建或更新 `chunk ID → 物理位置` 的内存索引；否则 compaction 移动记录会让持久 inode 指针悬空。检查数据边界、版本和校验后再使用命中位置。
- 记录不可变，并提供足够的 `(事务序号, 事务内序号)` 决定最新版本。GC 复制记录时保留其逻辑版本；恢复按逻辑版本而不是物理搬迁顺序确定最新 KV/目录项。同一逻辑版本的重复副本必须内容一致，否则失败关闭。删除标记在所有会被其遮盖的旧版本安全退出可见集合前不能丢弃。

这不意味着每次 64 B 写只消耗 64 B：记录头、对齐、inode/目录信息、checkpoint、碎片和 GC 都要计入。对连续写入，较小 chunk/extent 可能增加元数据和读放大；要通过负载实测选择，不预设某个尺寸全局最优。

### 2.2 根、恢复与字节范围

v4 的 checkpoint 至少标识格式、递增代数、已提交段集合/manifest、当前追加段的有效边界和校验/提交词。关闭段的有效区间由不可变 manifest 确认；常规追加只推进当前段的已提交边界，避免每次写都重写完整 manifest。一个事务跨段时，所有涉及的段与有效区间也必须通过**同一个候选根**发布。

1. 在未被旧根使用的区间准备不可变数据和必要元数据。追加到仍被旧根引用的开放段时，只能写两个有效根各自保护的有效区间之外、且不与这些区间共享缓存行的位置；不能证明安全时另开未引用的段。不得改写旧记录或旧段描述。
2. 刷写全部新记录、必要 manifest 和元数据并完成排序屏障。缓存行大小及持久域是平台参数，不能把示例中的 64 B 当成所有硬件的保证。
3. 对非活动 checkpoint 槽，按「先使旧提交词失效并持久化 → 写并持久化候选头 → 原子写最终提交词并持久化」发布。文件 `fsync` 成功在最后一步完成之后返回；后台 GC 或退役旧槽可能另外发布 checkpoint，不计作前台路径天然只有一次总提交。
4. 恢复选择合法的最高代根，只重放该根 manifest 与已提交边界内的完整记录；忽略边界外提前写回的未提交内容。验证格式、范围、段代数、记录校验、版本与对象引用，不能把未提交尾部扫描成已提交数据。

这里假设提交词按所用平台要求对齐且故障原子、flush/fence 到达声明的持久域，校验碰撞不发生。真实校验和有碰撞概率；设备损坏、恶意介质和未声明的硬件故障不属于该假设。

当前 v3 的 run 校验覆盖整页。若优化直接读取，校验函数必须是**只读**的：现有 `page_checksum()` 会临时清零传入缓冲中的校验字段，不能直接对已提交 PMEM 原地址调用。即便取消整页复制，整页校验仍会读取整页；新的读计数必须覆盖直接地址访问和校验，不能因绕开 `pmdev_read()` 而虚减。

### 2.3 有界空间回收

借鉴 FCS 的不可变对象、有效根保护和安全 COW，而不声称现有或拟议系统实现了完整 FCS、持久分形树或硬件磨损均衡。

- 从当前根的精确 KV 最新值、活 inode/extent 和仍需保留的删除标记识别一个候选段的活记录；保留逻辑版本，复制到预留目的段，持久化后以新 manifest 发布。inode 或目录若由多条增量重建，须保留全部必需增量或先生成完整可验证快照，不能只保留最后一条局部更新。前台有未提交 KV/stream 时，不得清空或遗漏；维护与前台提交共享明确的事务/锁协议。
- **两个有效根引用的段都不可回收**。新根发布后，旧活动根可能仍在另一槽中指向被搬迁段；可在新根验证成功后再次发布相同逻辑根以退役旧槽，或等待后续提交完成退役。只有两个有效根和活动读者都不再引用时才可复用；当前全局锁可先避免并发读者悬挂，未来拆锁必须显式 pin/epoch。
- 前台和 GC 分别做预留。保留量至少考虑：最大允许在途事务、单次候选段搬迁的最坏编码/对齐大小、manifest/checkpoint 更新、双槽滞后及分配碎片。实际按可分配区间/段预检，不能只检查空闲字节总和。最大事务必须有明确上限；跨段事务和 1 MiB 文件测试必须包含其预留成本。
- 在低水位之前触发维护；若无足够暂存区、无可产生净空闲空间的候选、全部数据仍活跃或读者长期 pin，安全背压或返回 ENOSPC。**不保证任意 100% 占用时仍可持续写入**。阈值和写放大由长期工作负载测量，而非凭算法名称推断寿命。

v3 是不可变单链，任意删除链中间的 run 不能只改一个指针；它当前需要全链重写，若没有足够的不相交暂存空间就必须失败。上面的段 manifest 是 v4 的设计目标，不是 v3 已有的增量 GC。

论文可围绕三项**待完成并验证的系统贡献**组织：共享 KV/文件事务的一次根发布；字节范围记录、逻辑 chunk ID 与双根保护的段回收组合；将实际范围事件重放、负控与同契约性能消融结合。它们是否有足够学术新颖性还需与已有工作比较，不能因为组合了若干结构名就声称原创算法或性能领先。

## 3. 第一步：v3 一次根发布的可执行改造规格

现有普通文件通常执行 `pmfile_shared_sync → pmstream_flush → pm_seal → pmfs_commit`，随后 `pmfile_store_meta_mask → pmfs_commit`。建议仅在保持 v3 记录/根格式和现有接口语义的前提下，重构为：

1. 持 `pmfs_lock`，快照活动根与相关工作状态；在事务本地准备新文件 chunk、extent 和候选 inode，不先破坏已有 stream 或公开 KV 的待提交内容。
2. 冻结当前全局 memtable 中的**全部**待提交项，包括不属于此文件的公开 KV 或其他 stream 的内部项，与本文件新增记录一起封装。现有语义允许一次文件同步顺带封存其他待提交项，不承诺各进程间事务隔离；但绝不能丢弃这些项。全局 memtable 可已有 32 项，不能假设再容得下文件 chunk：必要时拆成多个符合 v3 上限的 run，顺序链接、各自校验，预检 run 数、序号、空间和索引上限。其他 stream 尚未 emit 的缓冲仍归原 stream 所有。
3. 使用**同一事务的预留位图**，以两个有效根的完整可达集合加上本事务已预留的 run/metadata 页为保护集，一次预留所有需要的页。不能先调用现有 `pmfs_alloc_runs()` 再独立调用 `pmfs_alloc_meta()`：后者不知道尚未发布的 run 预留，可能把同一可复用页分配两次。
4. 将所有候选 run 和 inode COW 写入并持久化；在私有状态中校验候选链和 inode。现有 `load_run()` 会修改活动索引、读取边界使用 `fs->tail`，必须拆分为不污染现有状态的验证，以及发布后的安全索引安装。
5. 用一个 checkpoint 同时发布候选 `run_head`、`inode_page`、未变的 `dent_page` 和候选 `tail`。最终提交词持久化成功后才清除**确实包含在提交内**的 memtable 项、更新 stream 状态和 DRAM 索引，并允许 `fsync` 成功返回。

提交词写入之前的普通失败应保留文件 dirty 内容及其他待提交项，丢弃事务私有预留，活动根不变；若已经使非活动槽失效，该槽不一定能恢复为原状，但活动槽必须仍可恢复。**最终提交词已经写入后**，早期写回可能已经使新根持久化，即使后续返回错误也不能假装必然回滚；失败结果可能已提交，应停止不安全服务或重挂载确认。真实实现不得在持久提交后因索引安装失败而恢复旧内存根继续写。

在历史 64 B 覆写路径恰好写 1 个 4096 B run、1 个 4096 B inode 和两次各 `48 + 8 + 8 = 64` B checkpoint 请求的假设下，单次发布的**静态估算**是 `8192 + 64 = 8256` B，相比历史软件请求 `8320` B 仅少 **64 B（约 0.77%）**。这不是实测结果，也说明单次提交主要减少提交次数/屏障及消除中间状态；要显著降低写请求，仍需后续变长记录、局部更新及计入 GC 的实验。

### 设计模型与限制

`python3 tools/check_txn_design.py`（也包含于 `make test-model`）用单个活动旧根、一个更旧根、新 run、新 inode 和一项无关待提交公开 KV，枚举每个操作边界上所有脏抽象行的提前回写子集。它检查两个有效根、成功返回后的新根、失败前待提交状态和空间不足预检，并验证七个有意错误能被发现：漏保护旧槽、重复预留、漏刷 run、过早发布、漏刷提交词、丢公开 KV、过早清空待提交项。

该模型只含一个事务和两抽象行/页，假设校验无碰撞及提交词原子；它没有运行内核 C，未覆盖多事务、读者、v4 GC 或任意工作负载。实际实现仍必须通过内核 W/F/D 范围事件重放、重启及真实代码级失败注入；不能将模型通过称为内核或硬件证明。

## 4. 实现与验收顺序

| 阶段 | 工作 | 必须通过的门槛 |
|---|---|---|
| A：保持 v3 | 一次事务预留、多 run 候选、一次根发布；保留 KV/CDC/stream 和 v3 格式 | 普通文件一次 `fsync` 的 checkpoint 次数；32 项满 memtable + 文件 chunk；其他 stream/公开 KV 未丢；预留重叠和 ENOSPC 负控；每个提交切点旧/新文件和 KV 重启 oracle；现有 VFS/GC 回归 |
| B：字节寻址 v4 | 可变长记录、段边界和 checkpoint manifest、逻辑 chunk ID、局部 extent 更新 | 64 B / 4 KiB 随机覆盖与追加，跨段/边界、短写及恢复；至少 1 MiB 文件与 128 文件的目标测试；旧 v3 卷不被破坏；校验损坏和未提交尾部负控。目标不代表当前已达到 |
| C：回收和 VFS | 段级 COW 搬迁、双槽退役、预留；扩大目录和文件能力，明确 unlink-open 等语义 | 两槽及活动读者保护、活公开 KV 和活 chunk、tombstone、崩溃后重复 GC、近满盘安全失败与恢复；长期写入下计入后台开销；VFS 限制逐项列出 |
| D：正式实验和论文 | NVDIMM 实验、匹配基线、消融、失败模型和论文更新 | 保留源码/镜像哈希、配置、原始结果、失败和可复现脚本；图表只使用已执行的负载及对应契约 |

各阶段先有可运行的故障与回归测试，再要求性能改进；若 v3 一次提交使某些负载变慢，应保留负结果，不强行宣称优势。

## 5. 实验方案与结论边界

1. **明确设备。** 分别标注 EMUL、实验 NVDIMM、NVDIMM+Zicbom。正式题面实验使用补丁 QEMU、独立 NVDIMM 后端并用 QMP/FDT 验证；当前 `tools/bench_perf.py` 的 EMUL 基准需要扩展，不能把现有 EMUL 数据改名为 NVDIMM。
2. **同工作量。** PMFS 与当前仓的 xv6 原生文件路径分别完成相同字节、offset、创建/打开/写/同步/读回/关闭、目录深度及成功次数。已有原生 `fsync` 适配为全局日志同步，且 virtio 当前不协商 `VIRTIO_BLK_F_FLUSH`；先如实报告该差异。若新增可选 native flush 基线，必须同时落实日志次序、错误处理并通过其故障 oracle；不能仅打开 feature 位就宣称契约等价。
3. **同 PMFS 契约消融。** 控制设备、编译参数和输入，只改变一次/两次根发布、整页/范围记录、CDC/固定分块、精确索引/回退、GC 等一个变量；报告延迟和实际测时吞吐，不只报比值。
4. **覆盖负载。** 测 64 B、256 B、4 KiB 变更覆写/追加，顺序和随机读，创建/删除/rename、目录查找、公开 KV，以及普通与 `0xC0` 偏斜键。共享对照的文件尺寸不超过原生 xv6 上限；1 MiB PMFS 扩展另列。近满盘按实际活数据、双槽 pin 与预留分别记账，长期多轮写入记录成功、背压、ENOSPC、搬迁和恢复。
5. **指标。** 报告成功事务 p50/p95、独立启动作为统计单位的吞吐及区间、失败数、记录/数据/元数据/checkpoint/GC 软件 store 字节、请求 flush 行数、索引与校验实际读取字节、空间占用。软件写请求比 = 全部软件 store 字节 / 成功同步的有效用户字节，含对齐和 GC；这不是器件物理写放大或磨损。相同内容覆盖与实际改变内容分开报告。
6. **故障证据分层。** 协议模型、内核实际范围事件的提前回写重放及负控、QEMU 进程杀启/NVDIMM 后端恢复分别报告覆盖和假设；追加损坏根/记录及近满盘失败。它们都不是物理断电实验。只有在独立确认故障原子性、缓存写回与持久域后，才可以谈真实平台的对应保证。
