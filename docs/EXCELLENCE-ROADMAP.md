## 1. 目标与判断标准

推荐定位：**在保留 xv6 根文件系统的前提下，实现经普通文件系统调用访问的 PMEM 文件系统子集；以可复现的持久化故障模型验证提交协议，再用语义对齐的实验分析软件路径成本。**

这不是完整 POSIX、生产级 VFS 或真实硬件性能研究。能否采用并行 `/pm` 命名空间、使用 QEMU 设备模型以及模拟故障模型，应在第一周与导师确认。若题目要求根文件系统替换或真实硬件，必须另行增加工作量，不能把并行子系统冒充完成。

| 原题要件 | 必须形成的证据 | 当前状态 |
|---|---|---|
| 映射 QEMU 模拟 NVDIMM | 可识别的独立设备及后端、设备地址/大小、页表映射、与普通页分配器不重叠 | 目前仅有额外 RAM 窗口，**不是 NVDIMM 设备** |
| 字节寻址、去块设备抽象 | 普通文件 API、持久化偏移布局、数据路径调用计数；PMEM 文件数据不经 `bio/log/virtio` | 有专用文件 syscall 和 PMEM 页设备；不是普通 xv6 文件路径，仍整页写元数据 |
| 缓存行刷写与崩溃一致性 | 实际指令与平台假设、提交不变量、两次启动文件字节校验、有故障模型的崩溃矩阵 | 当前行遍历不执行缓存刷写；现有测试不足以证明掉电安全 |
| 对比延迟和吞吐 | 同操作、同数据量、明确持久语义的原始样本、统计和归因；结果如实报告 | 旧基准工作量、读取和持久语义不对齐，不能支撑加速结论 |

**优秀目标**不是给现有 `PASS` 再加数量，而是让“设备是什么、什么操作已持久化、故障后允许什么、实验比较的是什么”都可独立复核。核心贡献宜表述为“xv6 上的持久化协议实现与可重放验证”，不要声称首创或超越生产系统；对照 PMFS、NOVA、BPFS 及已有崩溃测试工作写清继承与差异。

### 研究问题与候选贡献

- **研究问题：** 在明确缓存块、持久域及故障原子性假设后，xv6 怎样以可恢复的文件提交替代块日志路径；只刷脏范围能否在相同提交语义下减少软件刷写工作量？
- **H1（一致性）：** COW 对象图先于 checkpoint 提交字持久化，可使单文件同步的恢复结果落在“上一完整版本/本次完整版本”集合。用有界崩溃状态空间和删 flush/drain 的负控检验；不把通过当作任意硬件/并发下的形式化证明。
- **H2（轻量化）：** 一个数据阶段中，窗口大小为 `W`、缓存块为 `C` 且二者对齐时，全窗口方案请求 `W/C` 个块；若待刷写范围覆盖 `K` 个不同块，合并后的范围方案该阶段请求 `K` 个块。必须另计各阶段重复刷写、checkpoint 和 drain，测量其管理开销；QEMU TCG 只能报告软件请求/模拟时延，不能称真实介质流量。`K < W/C` 是有待实验覆盖的工作负载假设，不是性能结论。
- **候选贡献及限制：** ① 面向 xv6 普通文件 API 的 COW 布局、提交不变量和恢复实现；② 面向该协议的可重放有界故障检查器、覆盖统计与能抓错的负控；③ 同语义的范围刷写消融和 xv6 对照数据。BPFS 等已有 COW，NOVA/PMFS 已研究持久内存文件系统，CrashMonkey、PMTest、Witcher 等已有自动故障/一致性测试；本课题应比较适用范围、实现及证据，**不声称首创 COW、刷写或崩溃测试**。贡献须在实际代码、实验和文献核对完成后再定稿。

## 3. 平台先行：真实设备模型与刷写能力是两个独立门槛

### G1：QEMU 设备可行性，第一至第二周决策

1. 固定 QEMU 版本和构建选项，检查 `-machine virt,help`、`-device help`，再**实际创建**设备并保存错误/成功日志；只看到 `nvdimm` 类型名称不代表该 machine 能安放它。
2. QEMU 9.2 的 [RISC-V virt machine 源码](https://github.com/qemu/qemu/blob/v9.2.0/hw/riscv/virt.c) 中未看到 PC 那套 NVDIMM memory-device 接入；官方 [vNVDIMM 用法](https://github.com/qemu/qemu/blob/v9.2.0/docs/nvdimm.txt) 举例是 `-machine pc,nvdimm=on`。这不证明所有未来 RISC-V 版本均不支持，必须以选定版本的实际启动和地址树为准。
3. **首选：保留本仓 RISC-V 主线。** 如果所选 `virt` 不支持，给固定版本的 QEMU 做最小、可审查的设备接入：注册独立 `nvdimm` 设备和 file-backed memory backend；为 memory-device 预留不与 DRAM/PCI/MMIO 重叠的 GPA 区间，完成必要的 machine plug 和静态设备描述（如 FDT `reg`）；xv6 从设备描述或经核验的固定配置取得区间，映射到内核页表并排除出 `kalloc`。当前 [`entry.S`](../kernel/entry.S#L8-L19) 会覆盖启动时的 `a1`，也没有 FDT 解析；若选择 FDT 发现，须先保存 boot 参数、校验和解析设备树，不能假装已有设备发现。具体 QEMU 接口以所选版本源码和 PoC 为准，不能仅改命名。保存 QEMU 补丁、上游版本/commit、构建和启动命令；**不把完整 QEMU 源码或大镜像提交进仓库**。
4. 验收须同时给出：启动参数包含实际 `-device nvdimm`（若采用该方案）、QEMU 的 `info memory-devices`/地址树或等价设备证据、FDT/固件描述、独立后端文件、guest 打印 GPA/大小、映射读写，以及 RAM/设备范围不重叠检查。常规启动不使用整机 RAM 文件冒充设备。
5. 若两周内设备 PoC 不通，明确选择：扩展 QEMU、另做 x86 xv6 移植（成本高、不是当前 RISC-V 内核的简单开关），或经导师书面确认改为“独立文件后端 PMEM/NVDIMM-like 设备”。后一条**不自动满足题面中的 NVDIMM 设备要求**。`virtio-pmem` 是另一种半虚拟设备，也不能直接叫 NVDIMM，且需先验证 machine 支持及其单独的 flush 协议。

文件后端和 `share=on` 不等于宿主断电后持久。QEMU 官方 vNVDIMM 文档对 DAX、`pmem`、`share` 等条件有明确限定；普通宿主文件仅用于模拟和进程重启实验。

### G2：RISC-V 缓存块指令与持久域契约

- 为所选 QEMU CPU/toolchain 显式启用并探测 Zicbom，确认缓存块大小、对齐和边界，设置允许 S 态执行所需的 `menvcfg.CBCFE` 等权限；把 `cbo.clean` 或 `cbo.flush` 封装进 `kernel/pmem.c`，配合对应内存类型要求的有序屏障。禁止静默回退成“读一遍”。
- 验收包括反汇编中存在指令、guest 实际执行无非法指令异常、禁用扩展时明确失败、跨行/零长度/越界测试和指令调用计数。仅看 `flush_lines` 不够。
- **指令和内存顺序不自动定义断电持久域。** 明确假设：缓存块操作加平台规定的 drain 能把目标数据送至持久域、对齐 8 字节提交字具备故障原子性；不支持这些假设的平台不能宣称该保证。
- QEMU 9.2 TCG 的 [CBO helper](https://github.com/qemu/qemu/blob/v9.2.0/target/riscv/op_helper.c#L242-L248) 明确不模拟缓存层级。因此，即使 guest 执行了 CBO，也不能靠普通 QEMU 杀进程证明缓存失效、落介质顺序或物理掉电安全。下一节的故障模型用于验证**声明的假设下**的协议，不伪装成硬件实测。

## 4. 推荐系统结构与任务边界

```text
普通 open/read/write/close/mkdir/unlink/fstat + 新增 fsync
       ├─ /pm/... → PMFS fd/目录/偏移管理 → COW inode/dentry/extent
       │                                   → 字节范围访问 + persist 接口
       │                                   → 独立 PMEM 设备 / 可重放模型
       └─ 其他路径 → 原 xv6 fs → bio/log → virtio-blk
```

- **最小文件语义：** `/pm` 路径分派，常规 fd 挂入 `struct proc`/`struct file`；`open` 的常用 flags、顺序 `read/write` 与 EOF、`close`、`fstat`、`mkdir`、`unlink`，以及普通 `ls /pm` 所需目录项读取。新增 `fsync(fd)`；根仍为 xv6 fs。路径匹配必须区分 `/pm` 与 `/pmx`，跨文件系统链接、`rename`、`mmap`、权限和 `chdir /pm` 暂不承诺。
- **资源目标：** 至少 64 个文件、单文件至少 64 KiB、文件大小/偏移/名字越界及空间不足可检测。先限制为单写者/串行提交，其他并发支持必须在锁、fd 生命周期和测试完成后再宣称。标准 xv6 自身回归不得退化。
- **布局：** 使用带格式版本和边界检查的 offset，而非持久化内核指针。两个 checkpoint 槽分别指向不可变的 inode、目录和数据根；数据通过字节范围读取/写入，允许用 4 KiB 作为**分配单位**，但不能把每次更新都退化为全页或全窗口复制。旧 KV/CDC/索引保留为可选研究路径，不再作为文件正确性的必经依赖；保留/删减须披露，不把切分包装成自动去重。
- **版本与保护：** 新格式使用独立测试镜像和版本号。旧格式、不支持的版本、双槽均坏或越界时只报错/只读，不自动清空；格式化必须是显式操作。不会静默迁移或覆盖旧镜像。
- **可观测性：** 按操作统计 PMEM 直接读写、数据/元数据字节、刷写行、drain，以及 `bio/log/virtio` 计数。测量 `/pm` 文件数据路径时排除启动和其他文件系统活动；不能仅凭函数名断言绕过块栈。

## 5. 一致性设计：双槽必须保护完整对象图

下述为**待实现**的单写者协议；持久域、8 字节原子写、未发生介质任意损坏等是假设，不是 QEMU 已经提供的事实。

1. 从最近一次提交的根出发，在未被**任何仍受保护的 checkpoint**引用的空闲区建立新数据与 inode/dentry/extent 的 COW 版本；旧对象不原地覆盖。读取可以直接寻址，分配回收在边界检查后进行。
2. 对新数据和全部可达元数据执行范围 `flush`，然后 `drain`；记录这些范围，不扫描整个设备。元数据引用只使用有效范围内的 offset、长度和 generation。
3. 对非活动槽先持久化无效提交字，再写入包含新 root offset、generation、格式、长度和校验的槽头并持久化。此时旧活动槽仍可用。
4. 最后用**对齐且故障原子的 8 字节 store** 写有效提交字，刷写并 drain；只有之后才向 `fsync` 或元数据操作返回成功。校验覆盖槽头；校验只能检测损坏，不能替代提交顺序或将概率性校验冒充原子性。
5. 恢复时检查两个槽的标记、格式、校验、generation、offset 和对象图边界，选择最高有效完整根；若无有效根则报告错误，不自动格式化。重复恢复应幂等。epoch 回绕、坏块和非模型内的任意介质损坏需定义处理边界。
6. 只有在旧 checkpoint 不再需要回退、且不存在打开引用后，才能回收相应对象；需要回收时记录可达性并防止崩溃中复用仍受保护空间。初版可无后台 GC，但必须安全返回空间不足；长期测试再实现可证明安全的回收。

**最小承诺及 oracle：**

| 情况 | 目标行为 |
|---|---|
| 普通 `write` 成功、尚未成功 `fsync` | 运行中后续读应看到写入；崩溃后不承诺保留，也不一概声称一定消失。其他提交或 `close` 若使其持久化，须按实现定义和测试。 |
| 单文件一次 `fsync` 正在进行时崩溃 | 在单写者、无其他提交的测试模型下，恢复到该文件的上一完整提交或本次完整提交，不出现旧元数据指向半新内容。 |
| `fsync` 成功返回后崩溃 | 在声明的故障模型和持久域假设下，之前写入的文件内容与必要元数据可完整恢复；创建的名称需有明确的目录持久语义。 |
| `create/mkdir/unlink` 成功 | MVP 选择各自作为原子持久元数据事务；调用中崩溃可恢复旧或新状态，成功返回后恢复新状态。 |
| `close`、失败和空间不足 | 明确是否同步 dirty 文件；若选择更强的 close 提交，失败必须向调用方返回，不能丢失 dirty/error。未完成提交不能提前返回成功。 |

这比“未 fsync 必然不可见”更准确：未刷写数据也可能被硬件提前逐出到持久域。单文件 COW 与根发布决定的是**可达性和原子提交**，而非假设脏缓存一定丢失。

## 6. 验证体系：进程重启、模型崩溃、硬件掉电分开

### 6.1 持久化故障模型与可重放检查器（差异化重点）

建立模型后端：volatile 状态 `V` 与 durable 影像 `D` 分离；通过 PMEM 字节写/原子写包装记录每次 store 的地址、数据、顺序和粒度，记录 flush 范围及 drain。所有会修改 PMEM 的路径（包括 `memmove`、`memset` 和提交字）都必须走可观测入口；用代码审计、断言和测试发现未覆盖的直接写，并对编译器拆分 store 的可能性作保守建模，而不是把一次 `memcpy` 假定为原子写。正常设备后端仍直接访问映射，不通过 `bio`。

在每个关键切点构造模型允许的崩溃影像：模拟未刷写行**也可能提前逐出**、flush 后 drain 前的乱序或部分完成、多个 8 字节原子粒度的撕裂；drain 后此前发出的相关 flush 必须完成。对小的有界轨迹穷举允许状态，对较大轨迹用固定种子抽样；持久化模型的规则、范围和限制随结果发布。每次重启只使用生成的 `D`，不能偷偷复用 `V` 或普通共享文件里的未刷写数据。

针对 `create/write+fsync/overwrite/mkdir/unlink`，在数据写入、数据 flush、drain、槽失效、槽头写入、提交字、返回前后逐点注入；oracle 校验名字、大小、完整 payload 哈希、上一次已确认提交、引用边界和分配可达性，而不是只 grep 一行。至少对小轨迹做全状态穷举，并对较大轨迹执行 **1000 个固定种子案例**；记录实际切点、生成/通过/失败数、种子、镜像和最小反例。覆盖数不足就如实报告，不以目标数冒充结果。

**负控不可省：** 在测试构建中分别移除数据 flush、移除关键 drain、先发布根再持久化数据，或故意原地覆盖当前已提交的元数据；为每种负控构造确实违反上述 oracle 的场景，检查器必须找到反例。若一个变异在允许“崩溃中旧或新均可”的语义下仍合法，就不能强行声称它必须被抓到。有效负控发现不了错误，说明测试不充分，不能把绿灯视为证明。快回归可跑确定性子集，全量放夜间/发布前执行；模型内的穷举不等于对全部并发或真实硬件故障的形式化证明。

### 6.2 两次启动与其他回归

| 测试 | 待验证内容 | 边界 |
|---|---|---|
| 两次启动文件测试 | boot1 创建多文件、写不同内容并 `fsync`；关闭 QEMU；boot2 使用同一**独立 PMEM 后端**读取并逐字节/哈希校验。覆盖覆盖写、目录和删除；关闭启动破坏性自测。 | 测进程重启和真实文件恢复，不单独证明缓存掉电顺序。 |
| 模型注入恢复 | 逐切点生成持久影像，重启读取或运行同一恢复逻辑；至少将每类关键切点的代表镜像在 QEMU 实际重启校验。 | 结论限定于声明的状态空间与硬件假设。 |
| 坏槽/坏元数据/越界 | 单槽损坏回退可用根；两槽均坏、版本不支持、越界、半元数据应明确失败，原镜像不被改写。 | 任意介质损坏超出正常断电模型；回退可能丢失最新已确认版本，不能称为无损。 |
| 资源与语义 | 64 文件、64 KiB、短读、EOF、偏移、重开、无空间、失败返回、重复恢复。 | 限定声明的单写者子集。 |
| 原系统回归 | `usertests`、原生 xv6 `crash`；PMFS 自身独立用例。 | 原生块文件系统 crash 测试不等于 PMFS 崩溃测试。 |

现有 `make contract`、`contract-strict`、`contract-pmem`、`contract-pmem2` 是旧原型 smoke；它们可以回归，但不是上述强验收。未来可新增 `make test-pmfs-reboot`、`test-pmfs-crash-model`、`test-pmfs-negative`；**这些目标目前不存在**。分离正常启动与测试专用构建，并让测试只使用明确创建的临时镜像。

## 7. 公平评测：先验证语义，再谈性能

### 7.1 基线和工作负载

- **B0：** 原版 xv6 `fs+log+virtio-blk`；明确它的 `sync` 只等待日志，现有驱动没有设备 flush，不宣称物理掉电保证。
- **B1：** 若要比较更接近的持久语义，增加并单独标明具备 `VIRTIO_BLK_F_FLUSH` 的 xv6 基线：协商设备功能、实现请求、在日志数据→提交头→安装到主位置→清日志的必要边界 drain，并验证错误处理。记录 QEMU block cache/flush 和宿主文件条件；这也不能无条件证明宿主物理掉电安全。
- **P0：** 新 PMFS，逐文件 `fsync`；统一 payload、成功操作数、名称、目录、创建/读取/关闭/删除步骤。所有步骤同时计入或同时排除，读取必须检查长度和内容。逐次同步与批量同步分成不同实验，持久确认点一致才比较。
- **P1 消融：** 在同一 PMFS 和同一语义下比较“全窗口刷写”与“只刷 dirty 范围”，以及可选批量策略；核对模型测试均通过。不要把不同 API 或更弱持久语义的结果当作优化收益。

工作负载至少覆盖：① 8/64/512 B 小文件创建和持久写；② 4/16/64 KiB 顺序写及重读；③ 已存在文件覆盖；④ 目录创建/删除。分别报告创建、写、`fsync`、读和端到端；额外读写模式只有在支持相同 API 后才比较。设置不同规模但保证两边实际完成 **相同 N**；检查原生 `FSSIZE=2000`、inode 和 PMEM 容量，必要时共同调整实验容量或分批创建临时镜像，不将空间不足的操作算作成功。

### 7.2 测量和复现

1. 固定 QEMU 版本/TCG 或 KVM、CPU 数、内存、编译器/flags、主机、后端文件系统、QEMU 缓存选项、随机种子、镜像初态、commit 和测试命令；实验前关闭自测及测量区内串口打印。控制启动顺序，随机或交替运行 B/P；区分 guest 重启后的缓存状态与真正受控的宿主冷缓存。
2. `r_time()` 是 time CSR 计数，**不是 CPU cycle**。从所选平台设备树或配置取得并记录 `timebase-frequency`，`秒 = Δticks / frequency`；另记录宿主单调墙钟及 QEMU 计时模式，不将 TCG 时间当真实 PMEM 硬件时延。计时开销单独标注。
3. 每种配置至少 10 次独立运行，足量记录单操作样本（目标每工作负载累计 ≥1000 次成功操作），保存每次原始数值和失败数。输出端到端及各操作的 p50/p95/p99；吞吐为 `成功操作数 / 总用时`（ops/s），大文件另报 MiB/s，不从中位延迟倒推吞吐。配对运行间比值和 95% bootstrap 区间可作为统计报告；样本数不足时不硬报尾延迟。
4. 区分 `用户成功写入字节`、`软件实际写入 PMEM 的数据/元数据字节`、`flush 行请求次数 × 行大小`、`fence/drain 次数`、xv6 块 I/O 字节/次数。给出起止计数差、分母及是否包含 checkpoint/回收；软件计数不叫真实介质物理写放大。
5. 原始 CSV/JSONL、配置、脚本、图表生成命令和每次运行日志一起归档；大镜像、生成物放外部制品/忽略路径，不提交 Git。记录失败和负结果。若 PMFS 没有优势，分析瓶颈并在正确性不退化前优化；**不预先承诺加速倍数**。

QEMU 结果主要反映所选仿真器、后端和软件路径；块设备与 PMEM 的后端/缓存仍可能不同，调用计数和同语义消融支持解释，但不能自动归因全部差距，更不能外推真实 NVDIMM 数值。
